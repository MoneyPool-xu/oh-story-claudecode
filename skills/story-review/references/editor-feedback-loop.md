# 编辑退稿反馈闭环

编辑原话是高价值样本，但不是自动成立的通用规律。先保存证据、复现问题，再分层升级。

## 项目内结构

```text
反馈/
  编辑退稿/YYYY-MM-DD-{平台}-{编号}.md
  _feedback-state.json
  项目规则.md
```

- 原始记录只追加：平台、日期、稿件版本、编辑原话、投稿范围；不改写编辑措辞。
- `_feedback-state.json` 是反馈状态权威，记录 `raw / reproduced / project-rule / rejected / promotion-candidate`。
- `项目规则.md` 是派生视图，只放已由正文证据复现的项目级检查，不成为剧情事实来源。

## 处理顺序

1. 将原话拆成可证伪假设，例如“看点不足”拆为卖点不可见、主角无代理权、兑现无后果等候选，不直接生成一条万能禁令。
2. 在被投版本定位章节和短证据；无法复现记 `unresolved`，不得为迎合评语硬改。
3. 可复现的问题进入本书 `项目规则`，修稿后对同一版本重跑审查、冷读及适用的平台门禁。
4. 单次、单书反馈不得修改仓库级 Skill。至少经过多部独立作品、同平台同赛道的重复证据与反例检查，才输出 `Platform Pattern` 候选；跨平台仍成立才考虑 Core。
5. 升级提案必须带 `evidence_refs / counterexample / failure_condition / applicable_scope`，由维护者审阅后才能改全局规则。

反馈只能让系统更可证据化，不能让它把编辑的一句话过拟合成所有小说的硬公式。
